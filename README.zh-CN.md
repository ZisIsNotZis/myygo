<h1 align="center">myygo</h1>
<p align="center"><strong>把《游戏王》卡牌效果写成数据</strong></p>
<p align="center">一个紧凑的、lambda 驱动的 DSL：把卡牌描述收束成统一的十个字段的效果元组——读起来像文本，结构上像代码。</p>

> **归档中的设计草图。** 不能直接运行，不再维护，仓库内也没有宿主引擎。真正留下的是 DSL 设计和卡牌数据。详见[归档说明](docs/project-status.md)。

[快速开始](#快速开始) · [目前能表达什么](#目前能表达什么) · [结构](#结构) · [继续开发](#如何继续开发) · [路线图](#路线图)

## 为什么值得看

《游戏王》的卡牌效果是散文。实现它们时，条件、代价、目标和处理往往散落在各处的临时函数里。myygo 把中文卡牌文本放在对应效果数据的正上方，并让每个效果都走同一种结构：

```text
[ type, loc, cond, costCheck, cost, opCheck, opTarget, op, countLimit, flag ]
```

每个钩子要么是 `None`，要么是普通 lambda，参数由上下文推断（`c` 当前卡、`tp` 当前玩家、`tg` 目标、`re` 原因效果等）。取卡与区域操作可以链式书写（`Get`、`L.*`、`Cards.is*`、`Cards.spsum` 等），于是一个完整效果只需要紧挨着卡牌文本的几行代码。

这个仓库是设计草图，不是引擎：它展示的是编写层，以及一组真实卡牌条目。

## 快速开始

无需安装，没有依赖，也没有入口程序。先读约定，再读一张卡。

```bash
git clone https://github.com/ZisIsNotZis/myygo.git
cd myygo
sed -n '1,72p' script.py     # DSL 约定
sed -n '73,94p' script.py    # 第一张卡：中文文本 + 效果数据
```

之后顺着 `script.py` 往下读：每张卡都是一段中文文本，后面跟着它的效果列表。`script2.py` 用同一批卡重复了一遍，并尝试了一种更简短、但尚未完成的写法。

## 目前能表达什么

- **用同一种结构描述不同效果类型**——启动效果（`IGNITE`）、触发效果（`SUMED`、`DESTROYED` 等）、“进行时”触发（`ATKING` 等）、永续效果和召唤手续，都使用同一个元组。
- **链式组合判断与动作**——`L` 用来把方法调用变成可复用的 lambda，`Cards` 把零张、一张或多张卡统一成一个集合，`Get` / `Choose` 负责区域与选择。
- **表达次数限制与标志位**——每回合次数、共享计数器 ID，以及 `CONTINUOUS`、`NODISABLE`、`TOEQUIPER` 等标志。
- **让文本和逻辑待在一起**——每个脚本各有 11 条卡牌条目，中文文本就在效果数据上方。
- **不依赖任何库**——两个独立的 Python 文件，没有任何 import；提供全局符号的引擎被刻意留在仓库之外。

## 结构

```text
.
├── assets/logo.svg          项目标志
├── docs/project-status.md   来源与归档状态
├── script.py                DSL 参考 + 较完整的卡牌集
├── script2.py               另一版草稿：重命名常量，未完成的微语法
├── README.md                英文说明
├── README.zh-CN.md          本文件
├── LICENSE                  AGPL-3.0-only
└── .gitignore
```

源码里能看见三层：

1. **约定**——`script.py` 的模块 docstring（第 1–72 行）定义了十个字段、钩子参数、区域、标志位和辅助函数词汇。`script2.py` 抄了一份，但已有轻微漂移。
2. **辅助层**——`L`、`Cards`、`Get`、`Choose`、`Register`、`Draw`、区域常量和标志位。它们只被引用，并不在此定义。
3. **卡牌数据**——每张卡一个效果元组列表，前面是它的中文文本。两个脚本都带同一批 11 张卡；`script.py` 更完整。

宿主引擎、卡牌数据库和可执行入口都不在这个仓库里。两个脚本都没有 import，按现状也都无法通过 Python 解析。

## 如何继续开发

这是归档仓库，没有构建、测试套件或受支持的工作流。若要接着做：

1. 先读 `script.py` 的模块 docstring，它最接近规格说明。
2. 保持十个字段的结构和推断出来的钩子参数不变；否则就要同时改约定和所有卡牌。
3. 把 `script.py` 当作参考，`script2.py` 只是实验，不是后继版本。
4. 先修语法错误，再加新效果：`script.py` 在 `Choose(...)` 调用和 `[1, 1]` 次数限制之间漏了逗号（第 91–92 行）；`script2.py` 从第 308 行开始改用未声明的小写微语法（`ignite`、`hand|mzone`、`equip(...)`），最后一张卡也没有闭合。
5. 每张卡的中文文本继续放在对应效果列表的正上方。

## 未来设想

如果恢复开发，myygo 希望成为一个小型、可读的《游戏王》规则引擎的编写层：卡牌文本和可执行的效果数据并排放在一起，引擎小到可以通读。真正有意思的问题不是覆盖多少张卡，而是那些相互纠缠的复杂效果能否保持声明式，而不会长成第二门编程语言。
